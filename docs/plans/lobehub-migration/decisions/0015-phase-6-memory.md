# 0015 — Phase 6 memory system

**Pipeline, ported from `packages/memory-user-memory` in condensed form.** After each assistant reply the chat route starts a Cloudflare Workflow (`MEMORY_WORKFLOW`, class `MemoryExtractionWorkflow`, replacing the hourly Upstash Workflow). The workflow loads the topic's messages and runs: a **gatekeeper** call that decides which of five layers (identity, preference, experience, activity, context) hold something worth keeping, one **extractor** call per chosen layer that proposes `add`/`update`/`remove` against the user's existing memories, and a **persona** call that rewrites the rolling profile if anything changed. The prompts keep upstream's layer definitions and its strict rule that only durable, cross-conversation directives are preferences; they are shorter than upstream's and are the main thing to tune against real model output.

**Storage differs from upstream on purpose.** LobeHub uses six tables and eleven pgvector columns. Here the layers share one `user_memories` table with a `layer` column and layer-specific fields in an `attributes` JSON column, and each memory has **one** vector (title, summary and details together) in its own Vectorize index, `MEMORY_VECTORS` / `openchat-v2-memory` (1024 dimensions, cosine, user namespace, no metadata filter, so no metadata index is needed). Memory text stays in D1, so a vector alone reveals nothing and retrieval maps hits through D1 with a `user_id` check. `user_persona` keeps upstream's shape (text plus a version, no vector).

**Safety properties, all covered by seam tests.** An extractor may only change memories it was shown, of its own layer, owned by the same user. Extraction is idempotent per topic (`topic_memory_state` records how many messages were processed), so a retried workflow does not duplicate. Failure anywhere in extraction or lookup never fails the reply: the workflow create is caught in the route, and a failing search degrades to the persona alone. Vector index writes are best-effort because D1 is the source of truth.

**Memory is on by default, with an off switch.** This copies LobeHub's default. It costs extra model calls per reply (a gatekeeper every turn, layer extractors when it says yes) and sends conversation text to the same Workers AI provider used for chat. `memory.setEnabled(false)` stops both extraction and use immediately and keeps what is saved; `memory.clear` deletes everything including the persona and vectors. Both are on the Memory page. **Flagging this default for the user**, who may prefer opt-in.

**Retrieval.** Each turn embeds the latest user message and adds the persona plus the top 5 memories to the system prompt, framed as background to use naturally, not recite. The assistant message records the memory ids and titles it used in `metadata.memories`, and the UI shows "Remembered: …".

**Testing at the boundary.** A `memoryWorld` fake answers the gatekeeper, layer and persona calls from a mutable script (identified by role markers exported from `prompts.ts`), keeps a second in-memory Vectorize, and provides a fake Workflows engine. `WorkflowEntrypoint` can only be constructed by the runtime, so the workflow body lives in `runMemoryExtraction(env, event, step)` and the class is a three-line delegate; the fake engine runs the body, and only that `extends` glue is untested locally (a dry-run deploy checks the export). Ordinary test clients get a no-op workflow binding, otherwise memory-on-by-default would start a real local workflow per chat.

**Pending real verification:** the `openchat-v2-memory` index; that Workers AI models return parseable JSON for these prompts (`generateJson` retries once with the validation error, but has not met real output); and the real Workflows engine's retries and timeouts. There is no time-based sweep of idle topics yet; extraction is per reply. A `scheduled()` sweep belongs to Phase 14 with the other cron work.
