# 0016 — Phase 7 goals and task graphs

Upstream's goal system is the largest subsystem in the reference repo: 16 tables and 300+ files covering a manager agent that drives a CLI, supervisors, an exploration planner, recovery policies, work versions and traces. A literal port is not feasible here, so this phase builds the **core loop the plan's acceptance line asks for** and records what is left out.

**Data model (six tables).** `goals`, `tasks`, `goal_nodes`, `goal_edges` (`source` depends on `target`), `goal_node_decisions` (human gates) and `goal_events` (audit trail), named as upstream. Not ported: work versions, traces, task comments and dependencies (the graph edges cover dependencies), the exploration/supervision/seed layers, the cost budget (`max_total_cost`; only rounds and planning turns are budgeted), and projects/workspaces.

**The loop.** A goal has a supervising agent, a requirement ("what counts as done") and budgets: `max_rounds` (default 8, counting planning rounds that add tasks) and `maxManagerTurns` (default 12). Each **tick** either runs the ready frontier (up to 3 independent tasks in parallel, a task running once its prerequisites are delivered and receiving their results as context) or, when nothing is runnable, takes a **manager turn**: an LLM call over a snapshot of the goal and graph that answers with one action. `tasks` adds 1–10 tasks with `dependsOn` (existing node ids, or positions of earlier tasks in the same plan); `verify` adds an acceptance node depending on every delivered leaf task; `escalate` asks a person. The plan is **validated before anything is written**: a dependency must be a live node or an earlier task in the same plan, so the graph stays acyclic and one bad entry refuses the whole plan. Two refused plans in a row ask a person. A `verification` node is run by an independent reviewer that returns `pass` or `fail`; on `fail` the manager plans corrective tasks and verifies again; on `pass` with no open work the goal is `achieved`. Upstream's fourth action, `retry`, is omitted: failures go to a human gate instead.

**Failures and human gates.** A task that fails is retried once automatically; after 2 attempts its node is `blocked` and a **decision** offers _retry_ (a fresh attempt budget), _skip_ (retire the node) or _stop_. The manager's `escalate`, and repeated refused plans, open a decision node with _continue_ (the manager plans again, given the person's note) or _stop_. The goal pauses until every open question is answered, and resumes on the last answer. Stopping withdraws open nodes and tasks and cancels open questions.

**Scheduling.** A Cloudflare Workflow (`GoalRunWorkflow`, binding `GOAL_WORKFLOW`) loops `advanceGoal` as retried, durable steps until a tick reports nothing more to do (finished, paused, stopped), then hands over to a new instance after 200 ticks. This replaces both upstream's QStash scheduler and its in-process `local.ts` fallback; Queues are not needed. Waking a goal (start, resume, a gate answer) simply creates an instance. **A lease on the goal row makes duplicate or overlapping runs harmless**: only one tick runs a goal at a time, and a test proves two overlapping runs execute each task once. A tick that starts on nodes left `running` by a dead run puts them back in the queue.

**Executing tasks.** For now a task is one completion by its executor agent (`config.taskAgentId`, else the goal's agent), in its own topic so the work can be inspected. Those topics carry `metadata.taskId` and `topic.list` leaves them out of the chat list. There are no tools yet: code execution arrives with the sandbox in Phase 8.

**Tested at the seam**, with a `goalWorld` whose fake Workers AI plays the manager, the reviewer and the executor from a mutable script, and a fake Workflows engine that runs the real workflow body (`runGoalWorkflow`; only the trivial class delegate is untested locally, as in decision 0015). Mutation checks confirmed that dependency order, the retry limit, the round budget, plan validation and the run lease are each guarded by a test that fails without them. The check that a blocked node pauses a tick is deliberately redundant with the pause that follows a frontier run.

**Pending real verification:** how real Workers AI models behave as manager and reviewer (JSON reliability, planning quality, the strictness of the review), the real Workflows engine's step timeout (10 minutes per tick) against slow model calls, and cost, since a goal makes several model calls per round. **Not built (flagged):** the upstream layers listed above, goal cost budgets, a goal-level cron schedule, and goal templates.
