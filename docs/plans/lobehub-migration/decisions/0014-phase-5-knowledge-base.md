# 0014 — Phase 5 knowledge base / RAG

**Where things live.** The uploaded file is in R2 (`FILES` binding, bucket `openchat-v2-files`). Its chunk **text** is in D1 (`chunks`). Only the **vectors** are in Vectorize (`KB_VECTORS`, index `openchat-v2-kb`, 1024 dimensions, cosine), keyed by chunk id, in a per-user namespace, with `file_id` as the only metadata. A vector alone therefore reveals nothing, and retrieval always resolves text through D1 with a `user_id` check, so an orphaned vector (a file deleted while Vectorize was unreachable) is inert. Bucket and index names are deliberately not the legacy app's, matching the placeholder D1 id: nothing here can touch production objects until the Phase 14 cutover.

**Embeddings use the existing Workers AI wrapper**, not the `env.AI` binding (decision 0005): `@cf/baai/bge-m3` through the OpenAI-compatible `/embeddings` endpoint, behind the same Cloudflare-host guard and the same injectable `AI_FETCH`. `bge-m3` is multilingual and 1024-dimensional, like the LobeHub embeddings it replaces.

**A file is chunked, embedded and indexed inside the upload request.** Only text-based files are supported (`text/*`, JSON, XML, YAML, and common source and data extensions when the browser gives no useful type), up to 1 MB, so a request stays within Workers' subrequest and time budgets. A file whose indexing fails is kept and marked `failed`, with nothing indexed, so the user can see and delete it. **Flagging this for the user:** PDF, DOCX and other binary formats are not parsed (LobeHub's file loaders cover them); adding them, and moving indexing to a Queue or Workflow for large files, is follow-up work that does not change the data model.

**Retrieval.** Each turn embeds the latest user message, searches the files attached to the agent (directly, or through an attached knowledge base) and passes the top 4 excerpts to the model in the system prompt, presented as reference material rather than instructions (the excerpts are untrusted text). The assistant message records its sources in `metadata.retrieval`, and the UI shows them. Retrieval is best-effort: an embedding or Vectorize failure is logged and the turn proceeds ungrounded. An agent with nothing attached makes no embedding call. Only `ready` files are searched.

**Knowledge bases** are minimal: named collections of files (create, rename, add and remove files, delete without deleting the files) that can be attached to an agent in place of, or alongside, individual files. Attachments replace as a set (`agent.setKnowledge`), and every id must belong to the caller or nothing is written.

**Not verifiable locally.** Vectorize has no local simulation (a `wrangler` warning says so), so tests inject a fake index and a fake embeddings endpoint at the two boundaries. The fake is immediately consistent; the real index takes seconds to make new vectors queryable, so a question asked right after an upload may miss it. **Pending real verification:** create the index and its `file_id` metadata index (the index must exist before vectors are inserted; commands are in `DEPLOY.md`), then confirm a real `bge-m3` call, a real query and the `$in` filter. Until then, in `pnpm dev` the binding is a stub and uploads end up `failed`.
