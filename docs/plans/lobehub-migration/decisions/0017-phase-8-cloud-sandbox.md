# 0017 — Phase 8 cloud sandbox (code execution)

**Backend behind a small interface.** The app talks to a `SandboxSession` with four operations (`exec`, `readFile`, `writeFile`, `listFiles`); everything else (running a code snippet, editing a file) is built on those. The Cloudflare adapter wraps `@cloudflare/sandbox` 0.12.9 (`getSandbox(env.SANDBOX, "topic-<id>")`, a Durable Object plus a Container), replacing LobeHub's Market-SDK/OnlyBoxes backend as decision 0004 planned. `SANDBOX` is an **optional** binding, and a test-only `SANDBOX_BACKEND` override (like `AI_FETCH`) lets the fetch-seam tests substitute an in-memory sandbox. The SDK was typed against, but never run, so the adapter is unexercised until a container exists.

**Docker was not running**, so per accepted pre-flight decision 4 everything is built and tested against the fake, and real verification is pending. For the same reason the `containers` block is **not** in the main `wrangler.jsonc`: it makes `vite dev`, the test runner and `wrangler dev` build a Docker image, which would break them on any machine without Docker. `wrangler deploy --dry-run` was checked and works without it. The block, the migration and `sandbox/Dockerfile` are documented in `DEPLOY.md` for the Phase 14 cutover; until then agents just have no code tools.

**Tools ported (a core subset of upstream's 13):** `runCommand`, `executeCode` (Python, JavaScript, bash), `writeFile`, `readFile`, `editFile`, `listFiles`, as AI SDK tools with the same shapes. Not ported: background commands (`getCommandOutput`, `killCommand`), search/glob/grep/move, file export, credential injection and the uploaded-files sync. The system prompt is adapted from upstream's, minus the AWS specifics.

**Who gets tools, and when.** One sandbox per **topic**, so a conversation's files persist across its turns and never reach another conversation, and the model cannot address any other sandbox because the id is chosen by the server after the topic's ownership check. An agent must **opt in** (`chatConfig.sandbox`, off by default, since it executes code), the model must have a probed `functionCall` ability in the catalog (5 of 15 models; Workers AI advertises tools for all of them but several leak calls as raw text, decision 0012), and a backend must exist. The same tools are given to a goal task's executor agent (Phase 7), in the task's own topic.

**Limits and behaviour.** Paths are confined to `/workspace` (a guardrail against wandering, not a security boundary: the container is the isolation). Commands time out at 30 s by default and 120 s at most, output is capped at 16,000 characters per stream, and a turn is capped at 8 model calls. If a model hits the cap without answering, the reply says so instead of being empty. Tool calls in one step **run one at a time in the order issued** (a per-session queue), because they otherwise run concurrently and "write a file, then run it" would race. Tool errors are returned to the model as results, never thrown, so a sandbox failure never fails the reply.

**Recording.** The `messages` table only allows the roles system, user and assistant, so tool activity is stored in the assistant message's `metadata.tools` (name, input, capped output). `toTextStreamResponse` streams only text, so the runs appear under the reply once the turn finishes (collapsed by default), not live.

**Operational risks to weigh at cutover:** Containers is beta with no SLA; a sandbox can make outbound network requests and run arbitrary user-directed code on your account (cap `max_instances`, and consider restricting egress); each active conversation with code execution holds a container.

**Pending real verification:** build the image and deploy or run with Docker; confirm the adapter against a real container (exec exit codes and timeouts, read/write/list shapes, id normalisation); confirm Python 3 and Node are in the base image (the prompt claims them, and the Dockerfile installs them only if missing); confirm a real tool-calling model drives the loop end to end.
