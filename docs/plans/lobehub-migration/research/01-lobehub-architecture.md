# Research 01 — LobeHub reference repo architecture

**Source**: background research agent, exploring `../new/lobehub` (a full clone of `github.com/lobehub/lobehub`, v2.2.17), during the Phase 0 grilling session, 2026-09-20.
**Purpose**: understand what's actually in the reference repo before committing to a migration plan. Referenced throughout `MIGRATION_PLAN.md` and `decisions/`.

---

IMPORTANT CONTEXT FIRST — this is NOT the classic OSS "lobe-chat" repo
The repo at `../new/lobehub` is `github.com/lobehub/lobehub` (package name `@lobehub/lobehub`, v2.2.17; `git remote -v` confirms it), a newer/rebranded, vastly larger successor to the old "lobe-chat" project ("LobeHub organizes your agents into 7×24 operation... hires, schedules, reports on your entire AI team" per README.md). It contains huge amounts of functionality that classic lobe-chat never had: agent groups/task graphs, a device gateway, sandboxes, messenger integrations (Feishu/WeChat/QQ/iMessage/Line), Composio/Klavis tool marketplaces, goal tracking, memory/user-memory, OAuth device flow, RBAC, resource-transfer, a whole `src/business` + `packages/business*` SaaS layer, etc. `packages/database/src/schemas` alone has 174 exported Postgres tables across 65 files. A literal "one-to-one replica" of this specific repo is an order of magnitude bigger than replicating what most people mean by "LobeChat." Also notable: parts of the paid/business layer are already stubbed to `return null` in this repo and there are explicit comments that a private "lobehub-cloud" repo overlays this one (see `apps/auth/vite.config.rr.mts` comment: "A host repo that overlays this app (lobehub-cloud maps `@/business/*` and friends onto its own implementations)").

## 1. apps/server (the Hono backend) — narrower than the name suggests; most business logic is tRPC, not Hono

- `apps/server/package.json` (`@lobechat/server`) builds a standalone Node/Hono server (`vite-node ... src/router-hono/dev.ts` → `standalone.js`, listens on port 3011). It has **no wrangler.jsonc** — it is not deployed to Cloudflare Workers in this repo.
- Despite the name, `apps/server/src` hosts **two very different things** under one roof:
  - `apps/server/src/routers/{lambda,async,mobile,tools}` — **tRPC routers**, ~119 files under `lambda` alone (agent, aiChat, aiModel, aiProvider, session, topic, message, file, knowledge, plugin, task, usage, user, share, etc.), plus `async` (background doc/image/video processing, 9 files) and `tools` (composio/mcp/market/search, 8 files). This is where the real chat/agent/model CRUD and business logic lives.
  - `apps/server/src/router-hono/*` — **Hono apps** (`agent`, `workflows`, `webhooks`, `composio`, `devtools`), ~91 files. These are exclusively webhook/cron/queue-callback endpoints: QStash-signed agent execution steps (`/api/agent/run`, `/api/agent/tool-result`), messenger webhooks (bot callbacks, OAuth), Casdoor/Logto auth webhooks, and Vercel-cron-triggered workflows (nightly review, memory extraction, goal sweep, task watchdog, topic auto-summary).
- Critically: **tsconfig.json line 29 maps `"@/server/*": ["./apps/server/src/*"]`.** The Next.js app imports `apps/server/src/routers/lambda` directly as source code (not over HTTP): `src/app/(backend)/trpc/lambda/[trpc]/route.ts` does `import { lambdaRouter } from '@/server/routers/lambda'` and serves it via `fetchRequestHandler` from `@trpc/server/adapters/fetch`. Same pattern for `async`, `mobile`, `tools` trpc routes.
  - Client calls confirm this: `packages/trpc/src/client/lambda.ts` hits `url: '/trpc/lambda'` — a same-origin relative URL to the Next.js app, not a separate service.
  - Likewise every `router-hono` Hono app is mounted into Next.js via optional catch-all routes, e.g. `src/app/(backend)/api/agent/[[...route]]/route.ts` literally does `import app from '@/server/router-hono/agent'; export const GET = handler; export const POST = handler;` (same for `composio`, `dev`, `webhooks`, `workflows`).
- **Bottom line for the migration**: "replicate LobeHub's Hono backend" is _not_ a faithful description of the API surface. The bulk of the business logic (chat, agents, models, sessions, files, usage, etc.) is tRPC procedures defined under `apps/server/src/routers/lambda` (backed by `apps/server/src/services/*`, 82 service subdirectories, and `apps/server/src/modules/*`, 13 modules) and bundled straight into the Next.js app's route handlers. The Hono layer is a narrower slice: async job callbacks, third-party webhooks, and cron/queue-triggered workflows (things that need a stable HTTP endpoint for QStash/cron/OAuth redirects to hit). A Cloudflare Workers rebuild means: (a) porting the tRPC `lambda`/`async`/`tools`/`mobile` routers (or re-implementing their `services/*` logic) as Workers-callable tRPC or plain handlers, and (b) separately porting the much smaller Hono webhook/cron surface (which maps naturally onto Workers Cron Triggers / Queues instead of QStash).

## 2. Database — Drizzle + Postgres, ~174 tables, several Postgres-only features

- Schema lives in `packages/database/src/schemas/*.ts` (65 files) + `packages/database/src/schemas/userMemories/`. `packages/database/migrations/` has **168 SQL migration files**.
- `grep -c "pgTable("` across schema files → **174 exported Postgres tables**. This is a large, mature schema (agents, agent groups, chat groups, topics, messages, tasks, goals, files, knowledge base/RAG, memory, connectors, device/gateway, RBAC, notifications, metrics, etc.).
- Non-portable / risky pieces flagged (do not translate cleanly to D1/SQLite):
  - **pgvector**: `packages/database/migrations/0005_pgvector.sql` (`CREATE EXTENSION IF NOT EXISTS vector`) and `packages/database/src/schemas/rag.ts` uses `vector('embeddings', { dimensions: 1024 })` for RAG document-chunk embeddings; also referenced in `packages/database/src/schemas/userMemories/index.ts`. D1 has no vector type/extension — this would need to move to Cloudflare Vectorize (or another vector store) entirely, not just a column-type swap.
  - **ParadeDB `pg_search` (BM25 full-text search)**: `packages/database/migrations/0090_enable_pg_search.sql` (`CREATE EXTENSION IF NOT EXISTS pg_search`) and `packages/database/migrations/0093_add_bm25_indexes_with_icu.sql` creates `USING bm25 (...)` indexes on `agents`, `topics`, `files`, `knowledge_bases`, `user_memories`, `chat_groups`, `user_memories_contexts`. No SQLite/D1 equivalent exists; would need FTS5 virtual tables (different schema/query model) or an external search service.
  - **`jsonb` columns**: used across **50 of the 65 schema files** (e.g. `metrics.config`, `metrics.metadata`, `connector.credentials`/`metadata`, message metadata, etc.). D1/SQLite has no native JSONB type — everything becomes TEXT with JSON1 functions; fine functionally but loses native indexing/operators Postgres jsonb offers.
  - **Postgres arrays** (`.array()`): used in 7 files — `agent.ts`, `device.ts`, `expertise.ts`, `oidc.ts`, `ragEvals.ts`, `user.ts`, `verify.ts`. SQLite has no array column type; needs JSON-text serialization + app-level (de)serialization.
  - No generated/computed columns (`generatedAlwaysAs`) were found in the schema set — that's one dimension that's _not_ a migration risk.
  - `drizzle.config.ts` (repo root) confirms the project is configured for the `postgresql` dialect.

## 3. Auth — Better Auth (not NextAuth/Clerk/Casdoor as the primary engine); apps/auth is a thin edge SPA shell

- The actual auth engine is **Better Auth** (`better-auth` npm package), not NextAuth. `src/auth.ts`: `export const auth = defineConfig({ ...authEnv.AUTH_COOKIE_PREFIX..., plugins: [] })` built via `src/libs/better-auth/define-config.ts`.
- Its Next.js API endpoint is `src/app/(backend)/api/auth/[...all]/route.ts`, which wraps Better Auth with `toNextJsHandler(auth)` from `better-auth/next-js`.
- SSO is pluggable via `src/libs/better-auth/sso/index.ts`, wiring provider modules under `src/libs/better-auth/sso/providers/`: Apple, Google, Github, Cognito, Microsoft, Auth0, Authelia, Authentik, Casdoor, CloudflareZeroTrust, GenericOIDC, Keycloak, Logto, Wechat, Feishu, Zitadel, Okta, plus built-in email/password (`BUILTIN_BETTER_AUTH_PROVIDERS`).
- Evidence of a _prior_ NextAuth/Clerk era still present as compatibility code: `packages/database/src/schemas/nextauth.ts` (legacy schema, presumably kept for migration), and comments in `src/libs/better-auth/define-config.ts` about being "Compatible with bcrypt password hashes migrated from Clerk" and a "Redirect old Clerk login route to Better Auth signin" note in `src/libs/next/config/define-config.ts`. So: this codebase **migrated off NextAuth+Clerk onto Better Auth**, with Casdoor/Auth0/Logto etc. as optional external IdP plugins, not the core engine.
- `apps/auth` (`@lobehub/auth`, deployed to Cloudflare Workers per `apps/auth/wrangler.jsonc`, worker name `lobehub-auth`) is **not** a separate auth backend — it's a thin, edge-rendered React Router v8 SPA shell containing only the login/signup/reset/verify/OAuth-consent/device-flow pages (`apps/auth/app/routes/{signin,signup,resetPassword,verifyEmail,oauthConsent,oauthDevice*,marketAuthCallback,...}.tsx`), each of which literally re-exports the shared component from the main app, e.g. `signin.tsx`: `export { default } from '@/features/Auth/SignIn'`. Its Worker entry (`apps/auth/workers/app.ts`) **proxies** any request under `/api`, `/oidc`, `/trpc`, `/webapi` straight through to `env.AUTH_API_BASE` (set to `https://app.lobehub.com` in `wrangler.jsonc`) — i.e. all real session/credential/SSO logic still runs in the main Next.js app; apps/auth just serves fast, edge-cached static/SSR login pages and forwards API traffic.

## 4. Community/Discover marketplace — one directory tree, `src/routes/(main)/community`

- Frontend routes: `src/routes/(main)/community/` with sub-trees `(list)` and `(detail)`, each further split by entity type: `agent`, `mcp`, `model`, `provider`, `skill`, plus (detail-only) `group_agent`, `organization`, `user`, `workspace`. This is the full marketplace: assistant/agent listings, MCP server listings, model/provider listings, skill listings, org/user profile pages.
- Related frontend state: `src/store/discover/` (incl. `src/store/discover/slices/mcp`), `src/features/CommunityAgentList`, `src/features/AgentMarketSubmission` (submitting an agent to the marketplace), `src/routes/(main)/community/features/McpEmpty.tsx`.
- Backend: `src/app/(backend)/market` (Next.js API), `apps/server/src/services/market/` and `apps/server/src/services/discover/`, tRPC surface in `apps/server/src/routers/tools/market.ts`.
- Gated behind the `market` feature flag in `packages/app-config/src/featureFlags/schema.ts`.

## 5. MCP support — modular "connector" concept, but touches tool-calling, tool store, and DB schema

- Client library: `src/libs/mcp/` (`client.ts`, `buildConnectorManifests.ts`, `connectorPermissionCheck.ts`, `patchManifestPermissions.ts`, `types.ts`, `utils.ts`).
- UI: `src/features/MCP/` (`MCPDetail`, `MCPInstallProgress`, `MCPSettings`), `src/components/MCPDepsIcon`, `src/components/MCPStdioCommandInput`, `src/components/Plugins/MCPTag.tsx`, `src/features/MCPPluginDetail`, `src/hooks/useMCPCategory.tsx`.
- State: `src/store/tool/slices/mcpStore/` — one of several sibling slices in `src/store/tool/slices/` alongside `builtin`, `plugin`, `customPlugin`, `composioStore`, `connector`, `agentSkills`, `lobehubSkillStore`. Structurally MCP is a peer of the built-in-tool/plugin slices, not hardwired into them.
- Server: `apps/server/src/services/mcp/` (incl. `contentProcessor.ts`), `apps/server/src/routers/tools/mcp.ts` (tRPC MCP client — validates `httpParamsSchema`/`stdioParamsSchema`, explicitly blocks stdio MCP outside Electron desktop: "Stdio MCP type is not supported in web environment").
- Data model: `packages/database/src/schemas/connector.ts` defines a generic **`user_connectors`** table with `ConnectorSourceType = { builtin, custom, ... }` and MCP-specific columns (`mcpServerUrl`, `mcpConnectionType`, `mcpStdioConfig` jsonb) sitting alongside Composio/OAuth connector config in the _same_ table/type. So MCP is one variant of a broader "connector" abstraction that also covers Composio and custom OAuth tool integrations — reasonably separable at the type/UI level, but the `connector` schema/table and its permission model (`connectorPermissionCheck.ts`, `ConnectorToolPermission`) are shared infrastructure, not MCP-exclusive code. Marketplace listing for MCP servers also lives inside `community/(list)/mcp` and `(detail)/mcp` (see §4).
- Also present: `apps/server/src/routers/lambda/klavis.ts` (Klavis, another MCP-adjacent hosted-tool service) — checked separately, see research/03 §4: fully dead code.

## 6. Pricing/billing — present but already stubbed out (proprietary/closed layer)

- UI: `src/business/client/BusinessSettingPages/{Billing,WorkspaceBillingBilling,WorkspaceBillingBudget,WorkspaceBillingCredits,WorkspaceBillingPlans,WorkspaceBillingUsage}.tsx` — **every one of these files in this checkout is a no-op stub** (e.g. `WorkspaceBillingUsage.tsx`: `export default function WorkspaceBillingUsage() { return null; }`; `Billing.tsx`: `const Billing = () => null;`).
- Routes: `src/routes/(main)/[workspaceSlug]/settings/{billing,budget,credits,plans,usage}/index.tsx`.
- Related: `src/features/PlanIcon/`, `src/features/Conversation/Error/PlanLimitCard/`, `src/business/client/features/StoragePayAsYouGo/`.
- Gating: `packages/app-config/src/featureFlags/schema.ts` documents `ENABLE_BUSINESS_FEATURES` as a server-side hard block, plus a `workspace` feature flag and "commercial license" flags (`commercial_hide_github`, `commercial_hide_docs`) with a comment: "the flags below can only be used with commercial license ... please contact us: hello@lobehub.com".
- As noted at the top, `apps/auth/vite.config.rr.mts` confirms a private "lobehub-cloud" repo overlays `@/business/*` with the real implementation — so the actual billing/Stripe-style logic is **not in this open-source checkout at all**; only stub components and DB-schema plumbing exist here.
- Entanglement check: `agentQuota` (schema `packages/database/src/schemas/agentQuota.ts`, service `apps/server/src/services/agentQuota/`, router `apps/server/src/routers/lambda/agentQuota.ts`) and `src/features/AgentQuotaCalendar` look like a usage-limit/quota mechanism that is architecturally separate from the (stubbed) billing pages — worth a closer look during actual migration to confirm it doesn't assume a billing backend, but nothing in this pass showed it calling into the stubbed Billing components.

## 7. Usage tracking/analytics — KEEP; both client dashboard and server aggregation over the `messages` table

- **Server-side**: no dedicated "usage_records" table — `apps/server/src/services/usage/index.ts` (`UsageRecordService`) computes usage/cost by querying `packages/database/src/schemas/message.ts`'s `messages` table directly, reading its `usage` jsonb column (falls back to `metadata.usage`/`metadata.performance` for older rows) plus `model`/`provider` columns, filtered to `role: 'assistant'`. Cost calculation lives in `apps/server/src/services/usage/cost.ts`. Exposed as a tRPC router `apps/server/src/routers/lambda/usage.ts` (`usageRouter`: `getAgentUsageStats`, `findAndGroupByDateRange`, `findAndGroupByDay`, `findByMonth`).
- Related tables that feed richer stats: `packages/database/src/schemas/agentOperations.ts` (`agent_operations` — per agent-run record with cost/duration), `packages/database/src/schemas/llmGenerationTracing.ts` (LLM generation tracing/observability), `packages/database/src/schemas/metric.ts` (generic polymorphic time-series `metrics`/`metric_points` tables usable for cost curves/dashboards).
- **Client-side**: `src/services/usage.ts` (`UsageService`, calls the tRPC router above) and the real analytics UI at `src/features/Settings/stats/` — `overview/{TotalTokens,TotalMessages,TotalTopics,TotalAssistants}.tsx`, `rankings/{ModelsRank,AssistantsRank,TopicsRank}.tsx`, `usage/{UsageCards (ActiveModels/ModelTable, MonthSpend, TodaySpend), UsageTable, UsageTrends}.tsx`, `visualization/{AiHeatmaps,HeatmapStats}.tsx`. Also `src/features/AgentUsage/UsageTrendChart.tsx` for per-agent usage, and `src/store/user/slices/settings/selectors/usage.ts` / `src/utils/operationUsageMetrics.ts` / `src/utils/workCumulativeUsage.ts` for aggregation helpers.
- Note: this is distinct from the _stubbed_ `WorkspaceBillingUsage.tsx` under `src/business/...` (see §6) — the real, working usage/stats feature is `src/features/Settings/stats/*`, not the business-billing one.

## 8. Agents feature and Models feature — top-level surface area

- **Agents**: routes `src/routes/(main)/agent/` (the agent detail/workspace shell, with sub-routes `(chat)` [the actual chat UI lives nested here], `profile`, `channel`, `docs`, `goal`/`goals`, `permission`, `self-learning`, `share`, `statistics`, `task`/`tasks`, `topics`) and `src/routes/(main)/agents/index.tsx` (agents list). Store: `src/store/agent/`, `src/store/agentGroup/`. Roughly three dozen `src/features/Agent*` directories (`AgentBuilder`, `AgentSetting`, `AgentSidebar`, `AgentProfileCard`, `AgentSkillStore`, `AgentTaskManager`, `AgentUsage`, `AgentGoals`, etc.) plus non-prefixed related ones (`ChiefAgent`, `HeterogeneousAgent`, `ConnectAgent`).
- **Chat**: not a separate top-level route — it's nested as `src/routes/(main)/agent/(chat)` (LobeHub treats "agent" and "its chat session" as one unit). Chat state: `src/store/chat/`.
- **Models**: no single `models` route directory; the surface is under Settings — `src/features/Settings/provider/` (provider list/config, e.g. `provider/(list)/ProviderGrid/Card.tsx`) and `src/features/Settings/service-model/`. Store: `src/store/aiInfra/` (AI provider/model infra state). Components: `src/features/ModelSelect/`, `src/features/ModelSwitchPanel/`, `src/features/ServiceModel/`, `src/features/OllamaModelDownloader/`. Backend tRPC: `apps/server/src/routers/lambda/aiModel.ts`, `aiProvider.ts`.

## 9. apps/share — public/shared conversation links, same "thin edge proxy" pattern as apps/auth

- Purpose: renders publicly shareable links for topics/chats, artifacts, and pages. Routes: `apps/share/app/routes/{shareTopic,shareArtifact,sharePage,catchall,homeRedirect}.tsx`; view components under `apps/share/src/features/{topic,artifact,page}/` (`SharedTopicView`, `SharedMessageList`, `SharedArtifactView`, `SharedPageView`, etc.).
- Deployed separately to Cloudflare Workers (`apps/share/wrangler.jsonc`, worker name `lobehub-share`, `vars.SHARE_API_BASE = https://app.lobehub.com`).
- Its Worker entry `apps/share/workers/app.ts` is functionally identical to `apps/auth/workers/app.ts`: any request under `/api`, `/oidc`, `/trpc`, `/webapi` is proxied straight to `SHARE_API_BASE` (the main Next.js app); everything else is served by the React Router v8 SSR handler. So, like apps/auth, **apps/share holds no independent backend logic** — it's an edge-rendered read-only UI shell that depends on the main app for all data (share content is fetched via `apps/share/app/lib/serverTrpc.ts` against the main app's tRPC). It genuinely _could_ be folded into the main app on Workers (as routes rendered by the same worker) since it has no own datastore or business logic; it exists as a separate deployable today presumably for independent edge caching/scaling of public share pages, not for any hard architectural reason.

## 10. File/image storage — generic S3-compatible client, readily points at R2

- `apps/server/src/modules/S3/index.ts` implements storage using the plain `@aws-sdk/client-s3` SDK (`S3Client`, `PutObjectCommand`, multipart upload commands, `getSignedUrl` from `@aws-sdk/s3-request-presigner`) — no AWS-only features used, purely the generic S3 API surface (bucket, endpoint, region, path-style, ACL are all configurable).
- Env config: `packages/env/src/file.ts` — `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_ENDPOINT`, `S3_INTERNAL_ENDPOINT` (separate internal-vs-public endpoint, useful for Docker/VPC setups), `S3_BUCKET`, `S3_REGION`, `S3_ENABLE_PATH_STYLE`, `S3_PUBLIC_DOMAIN`, `S3_PREVIEW_URL_EXPIRE_IN`, `S3_SET_ACL`.
- Since R2 exposes an S3-compatible API, this is swappable to R2 purely via env vars (custom `S3_ENDPOINT` pointed at the R2 S3 API endpoint + R2 access-key/secret) with no code changes required in this module — no native Workers R2 binding is used anywhere in this path.

## 11. AI/model provider abstraction — Cloudflare Workers AI provider already exists, implemented as an HTTP API client (not a native Workers binding)

- Provider registry: `packages/model-runtime/src/providers/` has ~90 provider directories (openai, anthropic, google, bedrock, ollama, groq, xai, deepseek, qwen, zhipu, vertexai, azureOpenai, replicate, togetherai, fireworksai, huggingface, mistral, cohere, perplexity, openrouter, ... and **`cloudflare`**). Static model metadata lives in `packages/model-bank/src/modelProviders/*.ts` (provider cards) and `packages/model-bank/src/aiModels/*.ts` (curated model lists).
- **Cloudflare Workers AI is fully wired**:
  - `packages/model-bank/src/modelProviders/cloudflare.ts` — provider card: `id: 'cloudflare'`, `name: 'Cloudflare Workers AI'`, `disableBrowserRequest: true`, `settings.sdkType: 'cloudflare'`, `modelList.showModelFetcher: true` (dynamic model listing rather than a hand-maintained list at the card level).
  - `packages/model-bank/src/aiModels/cloudflare.ts` (84 lines) — a curated static chat-model list (e.g. `@cf/deepseek-ai/deepseek-r1-distill-qwen-32b`, `@cf/qwen/qwq-32b`, `@cf/qwen/qwen2.5-coder-32b-instruct`, plus function-call-capable entries), each with `contextWindowTokens`, `abilities` (reasoning/functionCall), `family`/`generation` metadata.
  - `packages/model-runtime/src/providers/cloudflare/index.ts` — `LobeCloudflareAI` class implements `LobeRuntimeAI.chat()`. **Important nuance**: this calls Cloudflare's public REST API over HTTP (`packages/model-runtime/src/core/streams/cloudflare.ts`: `DEFAULT_BASE_URL_PREFIX = 'https://api.cloudflare.com'`, `fillUrl(accountID) => https://api.cloudflare.com/client/v4/accounts/${accountID}/ai/run/`), authenticated with a Bearer API token (`this.apiKey`) — i.e. it treats Workers AI as a remote provider like any other (works from Vercel/Docker/anywhere), **not** the native `env.AI.run(...)` binding that's only available when code executes inside a Cloudflare Worker itself. For a Workers-hosted rebuild, this existing implementation would work unmodified (just needs account ID + API token in env), but does not take advantage of the zero-latency/no-token native binding path that would be available since the target runtime _is_ Workers. (See `decisions/0005-ai-provider-keep-existing-wrapper.md` for why the current app's own equivalent wrapper is kept instead of either of these.)

Suggested files worth reading next during actual migration planning (not covered exhaustively here): `apps/server/src/services/agentRuntime/` and `packages/agent-runtime` (the orchestration layer tying model-runtime + tools + chat together), `packages/model-runtime/src/core/BaseAI.ts` (the `LobeRuntimeAI` interface every provider implements), and `src/libs/trpc/lambda/context.ts` (per-request context/auth wiring for the tRPC lambda router, needed to understand what a Workers port of that router requires).
